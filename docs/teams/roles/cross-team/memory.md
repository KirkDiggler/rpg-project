## Lessons

- Given a feature spanning UX and UI programming, UX takes the evaluation pass first and UI programming builds against it, because the experience definition is the programmer's input contract; reversing means programmers guess at experience and UX inherits code-shaped decisions. — 2026-10-22 (note 2026-10-22T234500Z-b2d4)
- Given a toolkit change players will feel, its PR stays open while consumers pin the branch's pseudo-version and the stack verifies it in-game: review-green means releasable, not landed. Zero-behavior providers may merge at review-green. — 2026-10-23 (note 2026-10-23T003000Z-d9f1)
- Given a feature ready to verify, the lead boots the stack from the wave's walk tree and hands the operator the port — operator-driven verification beats posted evidence whenever he's available. — 2026-10-24 (note 2026-10-24T010000Z-f6c2)
- Genre words carry weight: "law" read as permanent and deterred the review the docs exist to invite, so the genre section is "Standing Rules". — 2026-10-22 (note 2026-10-22T232000Z-a7c1, resolved same day on PR #678)
- Given the single-room dialect, a spec key lives in at least two carriers, the Go dungeonspec and the studio draft-file codec (readDraftYaml/importDocument), so a dialect change is not verifiable until both carry it; the web codec accepts what the toolkit accepts (carried verbatim, preserved on export) and refuses only what the toolkit refuses. Caught when augments validated at the api but were "unsupported field" at studio import. — 2026-10-24 (note 2026-10-24T014500Z-h9b1, [rpg-dnd5e-web#1330](https://github.com/KirkDiggler/rpg-dnd5e-web/issues/1330))
- In rpg-dnd5e-web the pre-PR gate is two commands, and a builder brief for that repo names both: `npm run test:run` for the suite (`npm test` runs vitest in watch mode and never exits, so a gate that goes silent is parked, not failing; interrupt it) and `npm run ci-check` for lint, typecheck and format, because a green vitest run can hide TS6133-class failures that only ci-check sees. — 2026-10-24 (notes 2026-10-24T020000Z-i4d9 and 2026-10-24T023000Z-j7e2, [rpg-dnd5e-web#1331](https://github.com/KirkDiggler/rpg-dnd5e-web/pull/1331))
- Given the foundation laid 2026-08 to 2026-09 (play/*, world, the composable encounter, resolution owning the bus), big changes stay possible when they make us better and never for no reason: a proposal that crosses a recorded decision names that decision and the evidence it rests on, because deliberate decisions are made on the data of where we have come from; a decision made and upheld under pressure is the foundation each area is seeded with. Graduating as R15 in [rpg-project#696](https://github.com/KirkDiggler/rpg-project/pull/696). — 2026-10-27 (note 2026-10-27T233200Z-k1e3)
- Given a question no recorded rule answers, ask first whether the foundation has shifted, whether the original goals are still the goals, whether they have been amended and whether they should be; then decide. "It depends" is the truth: even a line nobody can imagine reversing (play/* and world are never rulebook-specific) is not "never", a hard turn into a single game engine stays open if it makes us better, and long-term intent and what gets built need not always agree. So every decision line records its because, for the shift question to check against. Graduating into rule 13 in [rpg-project#696](https://github.com/KirkDiggler/rpg-project/pull/696). — 2026-10-27 (note 2026-10-28T001300Z-k3b4)
- Given the seeding of knowledge, it is not about being right about everything out of the box: we record what we know when we know it. Some areas are fuzzy, and each area gets its own big-picture treatment (why did we make this rule, does it still hold today) that recurs rather than running once as a backfill. — 2026-10-27 (note 2026-10-28T002300Z-k4c4, [rpg-project#676](https://github.com/KirkDiggler/rpg-project/issues/676))
- Given a new complex thing to implement, first look for the tool upgrade that would make it composable, pluggable and extensible, because those three qualities are what make a tool effective and impactful. Content is random but controlled random (procedurally generated, templated or pre-configured pieces such as puzzle pieces and table bundles), crowd-sourced in the spirit of Baldur's Gate 3: the easier it is to enter and the more generated bits we provide, the closer we are to the goal. — 2026-10-27 (note 2026-10-28T000400Z-k2a4, [rpg-project#694](https://github.com/KirkDiggler/rpg-project/issues/694))
- Given a batch of rulings for the operator, walk them in conversation one at a time, each with the evidence, the options and a recommendation, and record each answer on the owning issue as it lands; the issue is the record, never the venue, because a long issue full of checkboxes is one the operator cannot think inside, while one ruling given its own care is where the real reasoning comes out — 2026-10-28 (note 2026-10-28T142100Z-r3a2, https://github.com/KirkDiggler/rpg-project/issues/694)
- Given a finding with a bounded fix and no open decision, file a small explicit issue with a clear path (what by file:line, the steps naming the exact seam, done means with a greppable check, try it), because one output this process owes is a queue an overnight local coder can pick up without a conversation; a finding that needs a decision first gets the decision in conversation and the issue after — 2026-10-28 (note 2026-10-28T144000Z-r5a1, https://github.com/KirkDiggler/rpg-api/issues/1149)
