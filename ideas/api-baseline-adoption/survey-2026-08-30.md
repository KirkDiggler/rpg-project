## Headline

rpg-api's own code is very nearly ready for the frozen baseline: the entire adoption cost inside
rpg-api is **five field renames in four test files**, after which `go build ./...`, `go vet ./...`,
`go mod tidy`, and the full `go test ./...` suite (21 packages) all pass clean. The real work is
**not in rpg-api at all** — it is two tag-consistency defects upstream in rpg-toolkit that block the
build before rpg-api's code is ever reached. First, `behavior v0.2.2` is not a main-line tag: it and
`v0.2.0` were cut from an unmerged side branch and call `encounter.RememberedMember`, which
`encounter v0.39.2` deleted; the correct main-line pin is `behavior v0.2.1`. Second, and harder,
**no released `resolution` tag compiles against `dnd5e v0.122.2`** — the conditions rename (toolkit
#1319) never updated `resolution/contest.go`, toolkit `main` still carries the break, and each
module's own `go.mod` pin hides it from in-repo CI. That one needs a ruling, because the fix requires
a `resolution` re-tag and `resolution` is inside the active freeze window.

## Findings

### F1 — `behavior v0.2.2` is a side-branch tag and cannot be the baseline · **design conversation**

**Evidence.** After bumping the five briefed pins, `go build ./...` failed *inside the toolkit*, not
in rpg-api:

```
# github.com/KirkDiggler/rpg-toolkit/rulebooks/dnd5e/behavior
behavior@v0.2.2/basic.go:61:43: view.Remembered undefined (type encounter.MonsterView has no field or method Remembered)
behavior@v0.2.2/basic.go:98:47: undefined: encounter.RememberedMember
behavior@v0.2.2/basic.go:99:21: undefined: encounter.RememberedMember
```

Tag ancestry against `origin/main` (`git merge-base --is-ancestor <tag> origin/main`):

| tag | ancestor of main? | references `Remembered`? |
|---|---|---|
| `behavior/v0.1.0` | yes | no |
| `behavior/v0.2.0` | **NO — side branch** | yes |
| `behavior/v0.2.1` | yes | no |
| `behavior/v0.2.2` | **NO — side branch** | yes |
| `encounter/v0.39.0` | yes | — |
| `encounter/v0.39.1` | **NO — side branch** | defines `RememberedMember` |
| `encounter/v0.39.2` | yes | deleted (`turndriver.go`, `inteldelta.go`, `location.go`; −1783 lines net) |

**Cause.** `behavior v0.2.2` pins `encounter v0.39.1` (also a side-branch tag) and consumes
`MonsterView.Remembered` / `RememberedMember`. Those symbols live only on the ghost-pursuit branch
(dammitbilly0ne's freeze window, rpg-project#201). Main-line `encounter v0.39.2` deleted the whole
`inteldelta.go` / `location.go` / remembered-position surface. So the briefed baseline mixes one
side-branch tag into four main-line tags, and the set does not compile.

**Disposition.** Pin `behavior v0.2.1`. Verified: swapping to v0.2.1 clears all three errors with no
other change. The baseline definition in rpg-project#201 should be corrected, otherwise every
consumer that adopts it hits this same wall.

### F2 — no `resolution` tag compiles against `dnd5e v0.122.2` · **design conversation (blocking)**

**Evidence.** With `behavior v0.2.1` in place, one error remained, again inside the toolkit:

```
# github.com/KirkDiggler/rpg-toolkit/rulebooks/dnd5e/resolution
resolution@v0.24.3/contest.go:97:3: unknown field CharacterID in struct literal of type conditions.CreateFromRefInput
```

`conditions.CreateFromRefInput` across dnd5e tags (`git grep -A12 'type CreateFromRefInput struct'`):

- `dnd5e v0.122.0` — `CharacterID string`
- `dnd5e v0.122.1` — `CharacterID string`
- `dnd5e v0.122.2` — `MemberID string`  ← the rename landed here

`resolution v0.24.3` is the newest resolution tag, *is* an ancestor of main, pins `dnd5e v0.122.0` in
its own `go.mod`, and sets `CharacterID: targetID`. Toolkit `main` still carries the same line:

```
$ git grep -n 'CharacterID' origin/main -- rulebooks/dnd5e/resolution/contest.go
origin/main:rulebooks/dnd5e/resolution/contest.go:97:  CharacterID: targetID,
```

Toolkit `main` HEAD is `e71918c rename character id in conditions to member id (#1319)` — i.e. the
rename commit itself is main's tip, and it did not update `resolution`.

**Cause.** Toolkit #1319 renamed the field in `dnd5e` but not in `resolution`, which consumes it.
Because `resolution/go.mod` pins `dnd5e v0.122.0`, resolution's own module build still compiles and
in-repo CI stays green. The break is only visible to a downstream consumer that raises `dnd5e` to
v0.122.2 *and* builds `resolution` — which is exactly rpg-api, via `session`. This is the
fail-closed-not-fail-silent shape: a per-module pin masked a real incompatibility behind a green
suite.

**Disposition.** Needs an upstream one-line fix in `resolution/contest.go`
(`CharacterID:` becomes `MemberID:`) plus a `resolution` re-tag. `resolution` is one of the five
frozen modules, so this collides with the freeze — see Ruling R2. **To survey past it**, the evidence
branch carries a local `replace` of `resolution` to a patched scratch copy:

```
replace github.com/KirkDiggler/rpg-toolkit/rulebooks/dnd5e/resolution => /home/kirk/.claude/jobs/.../resolution-scaffold
```

That `replace` is **survey scaffolding only**. It is not a proposed fix, it must never merge, and it
is the reason the green results below are achievable today.

### F4 — the rename must be targeted, and the trap runs in both directions · **mechanical (with care)**

**Evidence.** `CharacterID` appears **~100 times across those same four files**. Only 5 are the
toolkit's condition structs. In `view_test.go` and `handler_test.go` the correct and incorrect
targets sit inside *one struct-literal block*:

```go
Features: []json.RawMessage{
    mustJSON(t, features.SecondWindData{
        Ref: refs.Features.SecondWind(), ID: "second-wind", Name: "Second Wind",
        Level: 3, CharacterID: id, Uses: 1, MaxUses: 1,   // <- STAYS CharacterID
    }),
    mustJSON(t, features.ActionSurgeData{
        Ref: refs.Features.ActionSurge(), ID: "action-surge", Name: "Action Surge",
        CharacterID: id, Uses: 1, MaxUses: 1,             // <- STAYS CharacterID
    }),
},
Conditions: []json.RawMessage{
    mustJSON(t, conditions.FightingStyleDefenseData{
        Ref: refs.Conditions.FightingStyleDefense(), CharacterID: id,  // <- BECOMES MemberID
    }),
},
```

The remaining ~95 are rpg-api's *own* domain fields and must not move:
`lobbyrepo.Member.CharacterID`, `orchcharacter.GetCharacterInput.CharacterID`, the suite fixture
`s.testCharacterID`, and the proto field `CharacterId`.

**Cause.** The rename was deliberately partial upstream: the 7 `features/` tags keep `character_id`
(verified `json:"character_id"` × 7 under `rulebooks/dnd5e/features` at v0.122.2) while the 22
`conditions/` tags move to `member_id`.

**Disposition.** Rename by *type*, never by regex — five explicit sites. The compiler catches
over-reach into `features.*Data` (unknown field `MemberID`), but it will **not** catch over-reach
into rpg-api's own `CharacterID` fields, which would compile happily and silently corrupt the lobby
and orchestrator contracts. Confirmed post-fix that all four `features.*Data` lines are unchanged.

### F7 — old saves' condition blobs are opaque to rpg-api and decode with empty `MemberID` · **design conversation (low stakes)**

**Evidence.** rpg-api stores `entities.Character`, which is a thin wrapper:

```go
// internal/entities/character.go:10
type Character struct {
    Data       *toolkitchar.Data `json:"data"`
    Appearance *Appearance       `json:"appearance,omitempty"`
}
```

`internal/repositories/character/redis.go` marshals and unmarshals that whole struct
(`json.Marshal(input.Character)` at :101/:173, `json.Unmarshal` at :142/:229). `Data.Conditions` is
`[]json.RawMessage` — rpg-api never looks inside a condition blob, and there is no migration,
rewrite, or field-level handling of them anywhere in production code. The decode happens on the
toolkit side of two seams:

- `internal/orchestrators/character/view.go:127` — `tkcharacter.Load(ctx, workingData)`
- `internal/orchestrators/character/orchestrator.go:743` — `character.LoadFromData(ctx, ..., finalBus)`

**Cause.** The persisted JSON key moved `character_id` to `member_id` for the 22 condition tags.

**Disposition.** A local dev save written before the baseline holds `{"character_id": "..."}` inside
a condition blob. On load the new struct finds no `member_id` and yields an **empty `MemberID`** —
silently, because unknown JSON fields are ignored. rpg-api itself is unaffected either way; it
shuttles the bytes. Under the project's no-backcompat rule this is free, but it is worth stating that
the failure mode is a silent empty string rather than a load error. See Ruling R3.

### F8 — the `.golangci.yml` depguard architecture rule is 100% dead · **design conversation (hygiene)**

**Evidence.** `no-rulebook-internals-in-action-handlers` lists **20 file globs**, all under two
directory trees:

```
**/internal/handlers/dnd5e/v2/encounter/*.go     (10 globs)
**/internal/orchestrators/encounter/v2/*.go      (10 globs)
```

Neither directory exists. `find internal/handlers -maxdepth 4 -type d` shows the deepest v2 tree is
`internal/handlers/dnd5e/v2/character`; `find internal/orchestrators -maxdepth 3 -type d` shows
`authoring, character, dice, lobby, session` and no `encounter`. So the rule matches zero files and
can never fire.

The rule's own comment claims otherwise, at length:

> "Architecture invariant: the core action-verb handler files in the v2 encounter package AND the v2
> encounter orchestrator method files must never import rpg-toolkit rulebook internals... This rule
> fires CI so drift is caught by the pipeline, not reviewer memory."

The sibling rule `no-rulebook-internals-in-session-handlers`
(`**/internal/handlers/dnd5e/session/v1alpha1/*.go`) **is** live — that directory exists.

**Cause.** rpg-api#801's rip-out deleted the guarded trees; the depguard rule was left pointing at
them.

**Disposition.** Unrelated to the baseline bump, but it actively misleads anyone reading the repo to
learn where the boundary is — including Billy's collaborator. Delete the dead rule or re-point it at
the packages that now hold the boundary. See Ruling R4.

## Rulings needed

- **R1 — Which `behavior` tag is the baseline?** `behavior v0.2.2` is a side-branch tag that cannot
  compile with main-line `encounter v0.39.2` (F1).
  *Recommendation:* correct the frozen baseline to **`behavior v0.2.1`**, the newest main-line tag;
  verified to build clean. Confirm this does not disturb Billy's ghost-pursuit window, which is where
  v0.2.2 and `encounter v0.39.1` legitimately live.

- **R2 — How does `resolution` get fixed, given it is inside the freeze?** No released `resolution`
  tag compiles against `dnd5e v0.122.2`, and toolkit `main` still carries the break (F2).
  *Recommendation:* treat this as a **freeze exception** — it is a one-line fix
  (`resolution/contest.go:97`) plus a patch tag `resolution v0.24.4`. The alternative, holding `dnd5e`
  at v0.122.1, abandons the rename that is the whole point of the baseline. Whoever owns #1319 should
  also confirm no other frozen module consumes `conditions.CreateFromRefInput`.

- **R3 — Do old local dev saves get a migration, or do we accept a silent empty `MemberID`?**
  Pre-baseline condition blobs carry `character_id`; the new struct ignores it and yields `""` (F7).
  *Recommendation:* **accept it**, per the project's no-backcompat rule — these are local dev saves
  only, and rpg-api holds the blobs opaquely so there is nowhere natural for a migration to live. But
  note the failure is silent; if that is not acceptable, the guard belongs in the toolkit's condition
  loader, not in rpg-api.

- **R4 — Delete the dead depguard rule, or re-point it?** All 20 globs of
  `no-rulebook-internals-in-action-handlers` target directories deleted by rpg-api#801 (F8).
  *Recommendation:* **delete it.** The boundary it guarded no longer exists as a code shape, and the
  live sibling rule already covers the session handler package. A rule that cannot fire while its
  comment insists it does is worse than no rule.
