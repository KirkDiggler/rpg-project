Layer 1 · Before the event bus

How Do You Save a Rule?

The first thing designed for the rules engine was storage. That is funny now: rpg-toolkit persists nothing. This is the journey from a generic array that made every consumer understand D&D, through moving boundaries, to a rule that can cross storage and wake up as behavior again.

01Before the toolkit
Architectural question 01

What was data unable to carry?

The Discord character creator read D&D reference content from Mongo. Its polymorphic choice[] could describe skills, equipment bundles, categories, counts, and choices nested inside choices. Mongo held that reference data successfully. The leak appeared after the read: every consumer still had to interpret each shape and remember what the selection meant.

First law: A transport shape is not the meaning of a rule.
022025-06-25
Architectural question 02

Where were the boundaries before code?

The repository began as one README and an ambitious dashed map: shared core/, generic systems/, and game-specific games/. It called the project TypeScript-first in prose, but the commit contained no implementation. On June 25 there were zero Go packages and zero working rulebooks. The dream was broad; the seams were folder names.

At this point: architecture was nouns connected by hope.
032025-06-26
Architectural question 03

Could storage be independent of the datastore?

The next day, eight storage and persistence documents landed across five commits, with two early versions already replaced. The strongest idea was repository injection: a module would declare only the access pattern it needed, and the host would inject an implementation. Redis, Mongo, memory, or files could sit behind the same seam. The idea survived, but not in one move. Repositories first left the toolkit. They returned later at one door around the SDK: depend on access, not technology.

Without an SDK layer to own a complete verb, injecting repositories through toolkit modules added more wiring than it removed.

Surviving promise: the backing store should not matter. Where the load-and-save lifecycle belonged was still unanswered.
04First working seam
Architectural question 04

Who should interpret Fighter?

The first freedom came from letting D&D code say what a Fighter grants and which decisions a Fighter requires. The host did not need a universal interpreter for every external choice shape. It could ask the rulebook for requirements, submit selections, and receive validation. Meaning moved closer to its owner. The result looked less generic—and became more extensible.

Freedom: put game meaning in the package that knows the game.
052025 → current
Architectural question 05

Which seams deserved to move?

Implementation turned the dashed map into a migration. Database ownership moved out to the host, while narrow repository contracts eventually returned at the session boundary. Game-specific behavior gathered in the D&D rulebook, while honestly shared mechanisms kept shared homes. Identity swung from strings and maps toward types everywhere, then settled on typed boundaries plus structured refs. Even Action changed meaning as real uses clarified what should travel and what should execute.

For a time, rpg-api owned the lifecycle itself: load the character, call the rule, inspect IsDirty(), and save what changed. The signal was useful. As conditions and turn state became more nuanced, the host was simply too far from the action to know every hydration and write-back moment.

Both storage moves removed complexity. First, repositories left toolkit internals. Later, the session SDK pulled load, dirty collection, and save timing out of rpg-api. The host still owns the implementations; the SDK now owns when to use them.
The pendulum mattered. A ref such as dnd5e:conditions:raging can cross a boundary without teaching the host the concrete type behind it. That is less rigid than typing every internal detail and safer than returning to magic strings.
Learned principle: specific first; extract after the second real use proves the seam.
06Persistence turn
Architectural question 06

What part of Rage can JSON save?

A live RagingCondition is two things at once. Its state—member, bonus, activation round, turns active, and activity flags—can be serialized. Its behavior is made of functions. Those functions decide how the condition reacts, and JSON cannot hold them. Saving the state is necessary, but a loaded bag of fields is not yet the rule players experience.

The gap: state can be stored; behavior must be reconstructed.
07Current pattern
Architectural question 07

Who brings behavior back?

The durable answer became a mirror. The host stores typed aggregate Data; polymorphic features and conditions sit inside it as opaque JSON. Each blob carries a structured ref. On load, the rulebook peeks at that ref, chooses its own loader, and restores the concrete object. The host can preserve Rage without knowing what Rage does.

IsDirty() survived. It remains the rulebook object’s honest signal that persisted state changed. What left rpg-api was responsibility for arranging the whole lifecycle around that signal. A session verb now loads, acts, saves, and returns.
The owner of behavior owns reconstruction.
08Current boundary
Architectural question 08

What boundary did that produce?

ToData composes downward: an encounter asks characters for data; characters ask features and conditions for JSON. Loading walks the ownership tree back up. There is no central serializer that understands every rule. The host owns database implementations and transport. The session seam declares the repository ports the host injects. The rulebook owns game meaning and reconstruction, and core keeps only the smallest vocabulary honestly shared across games.

The condition’s behavior is alive after loading. How can it reach combat without combat learning its name?
