# Dungeon YAML Spec v0.3

**Status:** proposed — Kirk ratifies the level cut on this PR.
**Supersedes:** the [Specimen Pack v0.2](https://github.com/KirkDiggler/rpg-project/issues/175#issuecomment-5185751479) comment lineage on rpg-project#175 as grammar/acceptance authority for `regions:` (see [Reconciliation notes](#6-reconciliation-notes), item 1) — including `ideas/dungeon-builder/design.md:5` ("The canonical target is Specimen Pack v0.2... superseding v0.1 as grammar authority") and `ideas/dungeon-builder/plan.md:7` ("## Current authority — Specimen Pack v0.2 is the target grammar and acceptance authority"), both still on `main` as of this PR and both named explicitly, not just superseded by implication (item 1's tracked follow-up debt). Aligns with, and adopts the version number of, `rpg-dnd5e-web`'s specimen pack (`src/concepts/dungeon-builder/specimens/`, currently v0.3) — going forward, spec vN and web-pack vN name the same contract level.

## 0. What this document is

This is the versioned contract between the builder side (which authors the dialect ahead of what the platform compiles — `rpg-dnd5e-web`'s `TARGET-YAML.md`/specimens) and the platform side (`rpg-toolkit`/`rpg-api-protos`/`rpg-api`, which implements against a ratified level). Kirk's ruling (verbatim, rpg-project session): "a sustainable way forward is for us to create the 0.2 spec and then they can build for that... let's get a solid 0.2 or 0.3 spec and start from there."

**Cadence:** the builder authors spec v*N*+1 while the platform implements spec v*N*. Proposals for the next level amend into a `vNext` draft. Version skew between what the builder has authored and what the platform has shipped is the **designed steady state**, not a defect to close — see `TARGET-YAML.md`'s "this gap is permanent, not a phase."

**Document `version:` vs. spec level — never conflate.** The dungeon YAML document's own `version:` field stays `1` for every construct in this spec, including everything newly promoted in the v0.3 cut. Per Kirk's settled additive model (rpg-project#175), a new optional field does not bump the document version; only a real incompatible/breaking change would, and none is proposed here. **Spec levels (v0.1, v0.2, v0.3, ...) are contract/pack versions** — they track how much of the dialect a conforming implementation is expected to accept, entirely independent of the one YAML `version:` integer a document carries.

This document is the **contract baseline**; it is not itself a request for platform implementation, and it does not claim any implementation, test, or merge evidence.

None of these are validated, echoed, or otherwise given wire acceptance by v0.3. A conforming v0.3 implementation continues to reject them exactly as today — but "reject" is not one failure mode. It is three, and they land at different places for an author or implementer to look:

1. **Decode-known, validate-rejected at a field path.** The field exists in the Go schema and decodes successfully; a semantic check then rejects it by name at its own path, leaving the rest of the document alone. `mount:` is this class: `PlacedEntry.Mount` is a real field (`dungeonspec/spec.go:86`) that decodes, and `Validate` rejects it explicitly and by path (`validate.go:351-353`, `"...mount: unsupported capability: mounted placements are not supported"`).
2. **Not in the schema at all — whole-document decode rejection.** The field has no Go struct tag anywhere the decoder's strict `KnownFields(true)` walk reaches, so the *entire* document fails to decode with an unknown-field error, independent of anything else in it. `height:` on a placement is this class today: it is not part of `PlacedEntry` (which carries `ref`/`at`/`facing`/`mount`/`blocks_movement`/`blocks_los`, nothing more), so a document with a placement-level `height:` never reaches semantic validation at all.
3. **Decode-known, validate-accepted.** Every construct §4 promotes into v0.3.

The `mount:` + `height:` row above names one tracking issue (#188) for two fields that are actually in different classes — read it as a location pointer, not a claim that both fail identically. §4.9's requirement that a `mount: wall` entry fail with a field-path error rather than a whole-document decode failure depends on `mount:` specifically being class 1, not class 2.

## 3. Ground rules for this contract

- **Strict, single-document decode is unchanged.** `dungeonspec.Decode` uses `yaml.Decoder.KnownFields(true)` and rejects multi-document input; an unrecognized top-level field fails the *whole* document, not just that key. Every construct promoted by this spec becomes a *known* field — it does not relax this discipline.
- **`version:` must be exactly `1`.** `dungeonspec.Validate` hard-rejects any other value (`rpg-toolkit encounter/dungeonspec/validate.go`: `if spec.Version != 1 { return fmt.Errorf(...) }`).
- **Coordinates are absolute pointy-top odd-q offset `[column,row]`** everywhere this spec uses a cell coordinate (`walls:`, `start:`, `place[].at`, `regions[].cells`) — the same space a compiled `FloorPlan` already uses. This is a corrected convention (rpg-project#179, 2026-08-04 erratum): "pointy-top" alone is incomplete; the offset scheme is odd-q, matching toolkit `core.HexFromPosition`.
- **Physical geometry and semantic scope are independent axes.** Space/canvas/floor and canonical wall/door edges own geometry and traversal; regions (§4.10) own gameplay identity. Neither axis derives the other.

## 4. Per-construct specification

### 4.1 Document metadata

```yaml
version: 1        # required; must be exactly 1
key: shrine-hall   # required; [a-z0-9-]+; must match the request's key
name: 'The Shrine Hall'  # required; display name
theme: crypt       # optional
height: 8          # decode-optional (missing decodes as 0); Validate's requirement is mode-dependent — see below
```

- **Decode vs. `Validate` — do not conflate.** `Decode` accepts a missing `height` as the Go zero value (`0`); decode itself requires nothing. It is `Validate` that enforces a floor, `spec.Height < minHeight` (`minHeight = 4`, `validate.go:74-76`), unconditionally first — before `minRooms` and everything else — but that check applies in **room-chain mode only**; canvas mode skips it entirely (§4.5's full mode-branch enumeration).
- **Room-chain mode** (§4.2 non-empty): `height` is the shared row bound for every room in the chain — real, load-bearing, and must be `>= 4`.
- **Canvas mode** (§4.5, `canvas:` present, `rooms: []`): `height` is decoded but **unused and unvalidated** — `canvas.height` is the authoritative row bound, with its own positive-integer rule (§4.5). Author tooling may write any placeholder value, including one below `minHeight` — the real specimen (`canvas.yaml:4`) emits `height: 1`. A conforming implementation must neither derive canvas geometry from top-level `height` nor reject a canvas document because of its value.

### 4.2 Room chain — `rooms:`

**v1, real today**, unchanged.

```yaml
rooms:
  - id: antechamber
    archetype: entrance   # entrance | chamber | corridor | boss
    width: 6
```

- The generator lays declared rooms out left-to-right in array order; each room's `start_column` is server-computed: `next.start_column = prev.start_column + prev.width + 1` (the `+1` reserves a connector-gap column between adjacent rooms).
- At least 2 rooms are required (`validate.go:77-78`, `minRooms = 2`).
- Exactly one room with `archetype: boss` must exist, and it must declare a `boss:` (`validate.go:257`; the chain-level "must have exactly one boss room" check, `"dungeon must have exactly one boss room, found 0"`, is stricter than and independent of the per-room "boss room needs a boss" check).
- **Superseded when `regions:` are declared** (§4.10): once a document declares any `regions:`, room `archetype` degrades to a geometry/generation input only — boss cardinality, entrance semantics, and spawn-rule validation bind to region scopes instead, never both at once for the same document.

### 4.3 Connectors — `connectors:`

**v1, real today**, unchanged.

```yaml
connectors:
  - { from: antechamber, to: shrine }
  - { from: shrine, to: vault, locked: { dc: 12, ability: dex } }
```

- Exactly `len(rooms) - 1` connectors are required; connector `i` must join `rooms[i]` to `rooms[i+1]` (`validateChain`, verified against source). `from`/`to` are **not independently authorable** — they are a pure function of declaration order, never an arbitrary pair, never a skip.
- `locked: {dc, ability}` is the one field a connector's author-facing surface actually varies. Omitted means unlocked.
- **This is a hard topological ceiling**: because a connector only ever joins `rooms[i]` to `rooms[i+1]`, a room-chain document can only express a **linear** dungeon — no branching, no loops, no room with two distinct connections. This is a property of the current chain encoding, not a permanent geometry model; branching topology is expected to arrive through the canonical-edge/region model (§4.7, §4.10), not by generalizing `connectors:`.
- A region-attachment door (§4.10) is a **distinct construct** from a chain connector: it never replaces, satisfies, or counts toward the `len(rooms)-1` requirement, even between the same two rooms.

### 4.4 Room-scoped placement — `place:` / `boss:` / `obstacles:`

**v1, real today**, base shape unchanged; `facing:` acceptance is new in this cut (§4.9).

```yaml
rooms:
  - id: hall
    obstacles:
      - { ref: 'dnd5e:props:bone-pile', count: 3 }
    place:
      - { ref: 'dnd5e:props:brazier', at: [1, 1], blocks_movement: true, blocks_los: false }
    boss:
      ref: 'dnd5e:monsters:skeleton-captain'
      at: [4, 3]
```

- `place[].at` and `boss.at` are **room-local** `[col,row]` — added to the room's compiled `start_column` to resolve an absolute cell.
- A room's door-row (`row == height/2`) is **illegal** for `place`, `boss.at`, and ordinary static reservations (contrast §4.6 `start:`, which is the one construct that may legally use it).
- `boss:` cardinality: dungeonspec requires exactly one `archetype: boss` room with a declared `boss:` (§4.2). There is no top-level (roomless) `boss:` in v0.3 — see §4.5.

### 4.5 Canvas — `canvas:` (rpg-project#192, Wave 0)

**Not started.** New in this cut.

```yaml
canvas:
  width: 20   # positive integer; columns [0, width)
  height: 30  # positive integer; rows [0, height)
rooms: []
```

- **Mode selection.** A document is in exactly one of two floor-source modes: **room-chain mode** (`rooms:` non-empty, §4.2) or **canvas mode** (`canvas:` present with `rooms: []`). Origin is `[0,0]`; bounds are half-open. Every in-bounds odd-q cell is structural floor — no holes, masks, or levels; no room chain, no connector-gap columns.
- **Combining non-empty `rooms:` with `canvas:` is unspecified by every source this spec draws from** — see [Reconciliation notes](#6-reconciliation-notes), item 4. Recommendation (not yet Kirk-ratified): reject the combination explicitly, mirroring the `rooms:` vs. `regions:` exclusivity question in §4.10.
- **Validation branches by mode — the full enumeration, not a sample.** `Validate` runs a fixed sequence (`validate.go:64` onward). Every check that ranges over `spec.Rooms` (the per-room width/archetype/pattern loop, the obstacles loop, the per-room `place:` loop) is vacuously a no-op on `rooms: []` and needs no branch. Everything else that is chain- or boss-coupled must be **explicitly** branched, because it either rejects unconditionally or crashes on `rooms: []` otherwise:
  - **Skipped entirely in canvas mode**, in `Validate`'s own call order: the `spec.Height < minHeight` check (`:74-76`, see §4.1); `len(spec.Rooms) < minRooms` (`:77-78`); `validateChain`'s connector-count-equals-`len(rooms)-1` check; `validateBossCardinality`'s error return (`:257` — `"must have exactly one boss room, found 0"` is the real, literal result for `rooms: []`, not a hypothetical). Because `validateBossCardinality` returns a `*RoomSpec` that three later checks dereference unconditionally, skipping cardinality without also skipping **all three** of `validateBossAxis` (`:262`, dereferences `bossRoom.Width`), `validateM1Restrictions` (`:168`, dereferences `bossRoom.Boss.At`), and `validateBossRef` (`:273`, dereferences `bossRoom.Boss.Ref`) means a nil-pointer panic, not a wrong-but-safe error. All six must be skipped together.
  - **Retained, but the floor source itself must switch from room-derived to canvas-derived**: `validateWalls` and `validateStart`. `validateWalls` computes its legal floor via `semanticFloorCells` (`validate.go:546`) — a *second*, independently-implemented room-only floor function, parallel to (not the same as) `authored_edges.go`'s `semanticDungeonFloorHexes` below. `validateStart` computes its own inline `starts`/`totalWidth` (`validate.go:444-455`). Both reduce to `totalWidth = 0` when `spec.Rooms` is empty, which collapses every in-bounds column check to `[0,0)` — verified by reading both: today a canvas document's `walls:`/`start:` are not merely unsupported, they are rejected as out-of-bounds *unconditionally*, for any coordinate. Both functions need a canvas-floor branch, not just "no branch exists yet."
  In-bounds checks otherwise run against `canvas.width`/`canvas.height` instead of a room's `start_column`/`width` footprint.
- **Top-level `place:` is accepted in canvas mode** (see §4.6) — a canvas document has no room to scope a placement to. It stays rejected in room-chain mode (`validateTopLevelPlace`, `validate.go:376-391`, `"top-level placement is not supported"`).
- **`start:` resolves against the canvas floor** (§4.8) — a floor-source substitution of the existing #177 resolver, not new resolution logic.
- **`FloorPlan` echoes canvas dimensions**: `rooms: []` plus `canvas.width`/`canvas.height` on the wire, with authored edges present as usual. `plan.md:13`/`design.md:11` ask for more than this — see [Reconciliation notes](#6-reconciliation-notes), item 6, an open ratification point, not resolved here.
- **Shrink-validation.** Growing `width`/`height` is trivial (always legal). Shrinking must fail with a named, specific error the moment any existing placement, wall endpoint, `start:`, or region cell (§4.10) falls outside the new smaller bounds — never a silent drop. Reuse the same "not a semantic floor cell" error shape `validateAndNormalizeAuthoredEdges` already uses for out-of-footprint edges.
- **Real, verified gap, runtime side**: `semanticDungeonFloorHexes` (`encounter/authored_edges.go:118-137`) — the function every *persisted* authored-edge (§4.7) endpoint is checked against at `InitDungeon` time, independent of the `validateWalls`/`semanticFloorCells` static-validation gap above — builds its floor set purely from `params.Regions` (room widths, left-to-right, minus the connector-gap column). It has no canvas/`width`×`height` branch today. Extending §4.7's authored-edge validation to canvas mode requires this function (or an equivalent) to also accept a canvas-derived floor. This is real scope, not a one-line check.
- **Non-goals**: no semantic-region/zone requirement — a canvas document with no `regions:` treats its whole floor as the implicit root scope (§4.10); no boss/monster content requirement (pairs with rpg-project#189, free-roam walkthrough, itself above v0.3); no locked-door grammar/binding decision (§4.7's `lock.options` acceptance boundary applies identically here).

**Acceptance criteria:**
- `PutDungeon(validate_only)` against a `canvas: {width,height}`, `rooms: []` document decodes successfully and returns a compiled `FloorPlan`.
- Static validation accepts an in-bounds canvas document and skips every room-chain-only rule; out-of-bounds content (placements, wall endpoints, `start:`) fails clearly against canvas dimensions.
- Shrinking `width`/`height` below existing content produces a named, specific validation error naming the offending construct, never a silent drop.

### 4.6 Top-level placement — `place:` (canvas mode)

**Not started.** New in this cut; canvas-mode-only.

```yaml
canvas: { width: 20, height: 30 }
rooms: []
place:
  - { ref: 'dnd5e:props:pillar', at: [10, 15] }
  - { ref: 'dnd5e:monsters:skeleton-captain', at: [5, 18] }
```

- Same field shape as a room-scoped `place:` entry (`ref`, `at`, `blocks_movement`/`blocks_los`; `facing:` per §4.9's scope boundary) — the only difference is `at` is unconditionally absolute, and there is no owning room.
- **Accepted only in canvas mode.** A room-chain document's top-level `place:` remains rejected (`validateTopLevelPlace`, `"top-level placement is not supported"`) — this spec does not change that gate.
- **No top-level `boss:`.** `validateBossCardinality` needs an owning `archetype: boss` room; there is no server-side concept of an unattached boss in v0.3. A canvas document's Boss tool has nothing to author against until a future spec level frees boss placement from the room requirement.
- Rooms remain **stable semantic regions** — organizational, not existential, placement containers. A canvas-mode top-level placement does not imply a synthetic room exists; it is real content with no owning room, full stop.

### 4.7 Walls — `walls:` (edge-native; rpg-project#176/#179)

**Live-verified** (rpg-api#769/rpg-toolkit#881, `tools/spatial/v0.6.0`/`encounter/v0.48.0`).

```yaml
walls:
  - { from: [7, 0], to: [7, 1], kind: solid }
  - { from: [7, 4], to: [7, 5], kind: door }
```

- **Shape**: flat, dungeon-scoped list of `{from, to, kind}`. `from`/`to` are absolute pointy-top odd-q `[col,row]` cells, **distinct and hex-adjacent** (hex distance 1 — not axis-aligned-only; "orthogonally adjacent" in this dialect's own wording means hex-adjacent). `kind` is `solid | door`.
- **Identity**: each edge has an undirected identity from its normalized (sorted) endpoint pair. A duplicate authored edge — including the reversed pair — fails validation.
- **Both endpoints must be compiled floor cells** of the document's active floor source (room-chain footprint, §4.2, or canvas floor, §4.5).
- **Overlay semantics are deterministic**: an authored `kind` replaces a colliding *generated, non-connector* physical edge. A collision with a **connector-generated** edge always fails validation — there is no mapping rule yet between an authored edge and a chain connector's own door.
- **Door identity**: a stable ID derived from the dungeon key plus the normalized absolute endpoint pair. An authored door starts **closed and unlocked**; a player may interact from either endpoint (symmetric reach — this is a real behavior change from the legacy single-position connector door, which is not retrofitted).
- **No reachability or region inference.** An inner authored edge changes movement/line-of-sight only; it never changes which region(s) own the cells on either side (§4.10), and semantic-region membership is never consulted to accept or reject an edge.
- **Runtime representation**: canonical wall geometry is carried on `HexRecord.edges`; the legacy flat `EncounterService.Space.walls` field does not exist and is not reintroduced. Authoring's `walls:` list compiles/projects into that canonical edge representation, deduplicating a shared edge rather than assigning it independently per side.
- **Lock grammar (`lock.options`) is documented, not accepted, in v0.3.** The canonical target shape (per the superseded-for-regions but still-current-for-this-part Specimen Pack v0.2 comment) is:
  ```yaml
  walls:
    - from: [8, 3]
      to: [9, 3]
      kind: door
      lock:
        options:
          - { ability: strength, dc: 12 }
          - { ability: dexterity, dc: 14 }
  ```
  One or more alternatives, ORed; each option has a valid ability and a positive `dc`; empty `options` and a lock on a non-door edge reject. Omitted `lock` means initially unlocked. **This grammar is recorded for forward compatibility; v0.3's executable acceptance criteria use unlocked doors only.** Lock *behavior* is a separate, unfiled rpg-project#175 follow-up and is explicitly not part of this cut's acceptance.

**Acceptance criteria:**
- Duplicate (including reversed), non-adjacent, and out-of-footprint edges fail validation clearly.
- An authored door edge never satisfies, replaces, or counts toward a chain `connectors:` requirement.
- An inner authored edge changes movement/LoS on both sides while every affected cell retains its existing region membership unchanged.

### 4.8 Start — `start:` (rpg-project#177)

**Live-verified** — overrides the generator-chosen `FloorPlan.entrance`.

```yaml
start: [1, 3]   # absolute [column, row]; optional/null
```

- Optional, top-level, absolute. Omitted or explicit `null` preserves today's generator-selected entrance exactly.
- May be in **any semantic room/region, regardless of archetype**. Must be a two-integer coordinate that is a member of exactly one room's (or region's, once §4.10 applies) floor footprint.
- **A room's door-row cell is legal for `start:` only** — the one exception to the door-row ban that governs `place:`/`boss.at`/ordinary reservations (§4.4). Connector-gap cells, including the connector door cell itself, are always invalid for `start:`.
- Resolves against **whichever floor source is active** (room-chain footprint or canvas floor, §4.5) — this is the same #177 resolver, ported to a second floor source, not new resolution logic.
- The toolkit reserves the resolved anchor plus a deterministic ordered party envelope (4 seats under the normal default `PartyCap`) *before* generating any blockers, for every seed; no relocation or fallback. A request for more seats than are reserved returns an explicit requested-vs-available error.
- `FloorPlan.entrance`/`SpaceData.Entrance` remain the single resolved-anchor wire truth — no new field. With an authored `start:`, they report the authored anchor verbatim, even outside an entrance-archetype room.

**Acceptance criteria:**
- Omitted/`null` fixtures retain today's entrance/spawn/generation behavior exactly.
- Static validation accepts a door-row start in any semantic room/region and rejects malformed shapes, out-of-footprint cells, connector gaps, and ambiguous/no-room membership.
- `PutDungeon(validate_only)` wire `FloorPlan.entrance`, persisted `SpaceData.Entrance`, and the first real `StartEncounter` player position all agree on the authored absolute cell.

### 4.9 Facing — `place:`/`boss:` `facing:` (rpg-project#178)

**Live-verified for one entry-type shape.**

```yaml
- { ref: 'dnd5e:props:statue-reaper', at: [4, 1], facing: SE }
```

- Vocabulary: `E | NE | NW | W | SW | SE` — six hex-native directions, 60° apart, canonical value order `E=0, NE=1, NW=2, W=3, SW=4, SE=5`. This is the one facing convention in the codebase; there is no separate rectangular compass.
- **Field is schema-known on every `place:`/`boss:` entry type**, but **validated acceptance is scoped to room-scoped, non-monster, `mount: floor` (default) placements only** — the exact boundary of the #178-approved delivery contract. Monster `place:` entries, `boss:` entries, and `mount: wall` placements (§2, above v0.3) decode `facing:` successfully but **must be rejected** with a field-path-specific validation error (`"facing only supported on room-scoped floor props"`), not stripped or silently ignored, and not a whole-document decode failure.
- **Top-level `place:` (§4.6) entries — corrected current behavior, and the canvas-mode acceptance boundary resolved.** `validateTopLevelPlace` (`validate.go:379-392`) loops every entry and checks `facing` **before** `mount`, reaching the `"top-level placement is not supported"` error (`:391`) only once it has confirmed *no* entry sets either. So **today**, a top-level entry with `facing:` set reports the facing field-path error first — `place[0].facing: unsupported capability: facing only supported on room-scoped floor props` — not the top-level message. (`TARGET-YAML.md`'s own probe table records this the other way around; this spec corrects it rather than inheriting the error.) That ordering is unchanged once v0.3 accepts top-level placement in canvas mode (§4.6), and the outcome for `facing:` specifically does not change either way: the #178-approved delivery contract scopes accepted `facing:` to **room-scoped** floor props only ("Only existing room-scoped floor-prop `rooms[].place[]` entries may carry facing") — a top-level entry is by definition not room-scoped, canvas mode or not. **A canvas-mode top-level entry with `facing:` set is rejected with the same field-path error as a monster/boss/`mount: wall` entry, regardless of whether top-level placement is otherwise legal for it.** This follows directly from #178's already-settled scope; it is not a new ratification point.
- Omitted/`null` `facing:` preserves existing orientation exactly; presence must be distinguished from absence through persistence (the toolkit does not collapse an explicit `E`/`0` to "no facing").

**Acceptance criteria:**
- All six values compile and render at the expected 60° orientations on a room-scoped, non-monster, floor-mounted placement.
- An unknown value fails validation with the accepted vocabulary named in the error.
- A monster, boss, or `mount: wall` entry with `facing:` set fails with the field-path-specific message above, not a decode error and not a silent drop.
- A canvas-mode top-level entry with `facing:` set fails with the same field-path error, whether or not the rest of that entry (sans `facing:`) would otherwise be accepted under §4.6.

### 4.10 Regions — `regions:` (rpg-project#180, Wave 1)

**Not started.** The largest construct in this cut. Full scopes semantics below — this section intentionally repeats what `ideas/dungeon-builder/design.md`/`plan.md` state at summary level, in the complete form the platform docs currently omit.

#### 4.10.1 Shape

```yaml
regions:
  - id: shrine-inner
    name: 'Shrine — Inner Sanctum'   # optional; id doubles as the label otherwise
    archetype: chamber               # optional; entrance | chamber | corridor | boss
    cells: [[9, 2], [9, 3], [9, 4], [10, 2], [10, 3], [10, 4]]
```

`RegionDoc { id: string; name?: string; archetype?: string; cells: [number, number][] }`. `cells` is a **flat list of absolute `[col,row]` pairs** — the complete, explicit extent of the region, not a bounding rectangle and not a run-length/mask encoding.

**`cells:` is the wire representation; `extent: {min,max}` rectangles are rejected as a representation.** The Specimen Pack v0.2 comment on rpg-project#175 used `extent: {min,max}` — that comment is **superseded by this spec** for region shape (see [Reconciliation notes](#6-reconciliation-notes), item 1). `cells:` matches `TARGET-YAML.md`'s settled shape, the #180 discovery comment's own concrete proposal, and every specimen the builder actually emits (`specimens/kitchen-sink.yaml`). A region need not be rectangular or even simply-connected across its full nested chain (only each region's own cell list must itself be contiguous — §4.10.3); an `extent:` rectangle cannot express that.

#### 4.10.2 The model: regions are scopes

Settled across five 2026-08-04/05 comments on rpg-project#180 (consumer position, refinement, representation/resolution, runtime convergence, platform decision checkpoint). This supersedes any flat/disjoint-only reading of an earlier discovery comment on the same issue.

1. **Every cell belongs to exactly one *innermost* scope; the implicit root replaces "regionless."** Unpainted floor belongs to the implicit root/generic region — there is no "unless regionless" special case anywhere in this model. Regions may include **any walkable cell**, including doorway/connector threshold cells — occupancy and door state never affect paintability.
2. **Hierarchy is derived from cell-set containment, never authored.** Two regions' cell sets may relate three ways: disjoint (siblings), strict subset (child/parent), or neither of those (equal or partial overlap, **forbidden**). There is no `parent:` field. A region's parent is the smallest strict superset among all declared regions, or the implicit root when none exists. A cell's *innermost* region is the smallest declared region containing it.
   - **Why derived beats a `parent:` field or structural nesting**: no donut problem (a parent's cells are its true full extent; deleting a child leaves the parent whole; repainting a child edits one list); the contradiction class (a child spilling outside its parent) is unrepresentable, since geometry is the only authority; a `parent:` field would duplicate what the cell sets already say, and duplicated truth drifts; flat lists keep diffs small and comments attached to the right list.
   - Because overlap is allowed only by containment, all regions containing a given cell form a **chain** — any two regions sharing a cell must be nested, hence comparable. This is what makes "the parent" and "the innermost region" well-defined, cheap lookups rather than an ambiguous multi-parent graph.
3. **Regions may nest arbitrarily deep**, not just one level — the shipped flat/disjoint model is exactly one level of leaves under the implicit root; nesting is a strict extension that breaks no existing document (flat non-overlap remains a valid degenerate case).
4. **Region boundaries derive from membership transitions and are never physical.** A region has a boundary wherever its membership meets a different region (including root). That boundary is a **semantic transition only** — open by default, impassable only where a wall edge (§4.7) independently exists there. **Region boundaries never become `FloorPlanEdge` records.** Space owns physical edges; regions never manufacture one by virtue of being adjacent to another region.
5. **Per-property resolution is independent per property, walking the containment chain innermost-outward.** A region's own declared properties (today: `archetype`; in future spec levels: audio/lighting/trigger scopes per the extension seam below) resolve by asking the innermost region first, then its parent, then *its* parent, up to root, and using the first scope that actually declares that property — **each property resolves this walk independently of every other property**. Example: the vault (innermost) declares `audio:` — vault's value applies. The vault is silent on `lighting:` — its parent (the crypt)'s value applies. Nothing in the chain declares a property — root's default applies. A region being silent on one property never forces it to inherit *every* property from its parent; each is resolved on its own.
6. **Enter/exit is stack semantics, not flat notification.** Entering the vault (nested inside the crypt) fires a vault-enter transition **without** a crypt-exit transition — containment means the crypt was never left. Exiting the vault fires a vault-exit and pops back to the crypt's own ambience/scope, again with no crypt-enter (it was already active). Enter/exit are crossings of the derived membership-transition boundaries from point 4, evaluated against the *whole* scope chain, not just the innermost region.
7. **Archetype authority follows scopes, exclusively.** When a document declares any `regions:`, boss cardinality, entrance semantics, and spawn-rule validation bind **only** to region scopes — room `archetype` (§4.2) becomes a geometry/generation input only, never a second, competing validation authority. A boss's cell must be a member of the applicable boss-archetype **region** scope; there is no double room/region validation, and a boss region painted inside a chamber-room is not contradictory by construction (the region wins).
8. **Painting, repainting, or deleting a region never invalidates structural floor, canonical edges, endpoint-derived door IDs, content, or content validity.** Carried, in nearly identical words, by four independent sources: `design.md:15`, `plan.md:27`, #180's issue body ("Settled model"), and the platform decision checkpoint (`5185024786`). Editing a region's `cells:` cannot alter floor, physical edges, or door identity, and cannot invalidate a placement, monster, or boss sitting on the affected cells. Removed semantics fall back to the enclosing scope (the parent, or root) — never to an error. Existing room-based semantic lookups are not renamed by this: once a lookup has resolved to an absolute location, it continues to resolve scope from that location regardless of later region edits. This is the invariant behind Kirk's own framing (#180, 19:27 comment): "deleting a region must never break props; that would be an authoring-feel disaster." **Physical door identity is, specifically, normalized-endpoint-derived and region-independent** (design.md/#180 body) — "connector door IDs remain physical-layout identities rather than being renamed by semantic repainting" (the checkpoint, verbatim). §4.10.4's own door-ID note states the connector case without this caveat; read it together with this point, not in isolation.

#### 4.10.3 Validation and invariants

Matches rpg-project#180's own acceptance criteria and the client-side `validateRegionCells` implementation that already enforces the same rules (`TARGET-YAML.md`'s "regions:" section, `regionGeometry.ts`):

- **Non-empty** — a region needs at least one cell. A single-cell region is allowed.
- **Hex-contiguous** — every cell in *one region's own list* must be reachable from every other cell in that same list via real hex adjacency (6-neighbor BFS/flood-fill, not 4-neighbor/axis-aligned). This is a per-region invariant on that region's own cell set; it is orthogonal to, and unaffected by, that region containing a nested child region's cells as a subset.
- **No duplicate cell within one region's own list.**
- **Overlap resolves to exactly one of**: disjoint (valid, siblings), strict containment (valid, parent/child), or equal/partial overlap (**invalid**, rejected).
- **`archetype`** is optional and resolves per §4.10.2 point 5 (innermost-outward, independent per property) when omitted. An explicit empty string or a value outside `entrance | chamber | corridor | boss` is rejected — omission and explicit-invalid are different failure classes.
- **Regions need not tile the canvas.** Sparse, disjoint regions with unclaimed cells between or around them are valid; a region is a claim about gameplay identity for the cells it lists, not a partition requirement.
- **An inner wall (§4.7) never splits, renames, or affects a region's `cells:` membership** — membership changes only through an explicit region-cell mutation, never as a side effect of wall/door editing.
- **Persistence**: source cell lists are authoritative and persisted; **derived parent ID and containment index are also persisted**, and `Load` must recompute both and reject if the recomputation disagrees with what was persisted (protects against a hand-edited or corrupted persisted derivation going stale).
- **Whether a document may combine non-empty `rooms:` with declared `regions:` at all is Kirk's call, not yet ratified here — this is narrower than whether regions win once both exist.** That regions supersede rooms for archetype/boss/entrance/spawn validation the instant any `regions:` are declared is already settled (§4.2, §4.10.2 point 7) and is not in question. What's open is only whether the combination itself should be flatly rejected outright, or silently tolerated with regions simply taking precedence as stated above. Recommendation (unchanged from `TARGET-YAML.md`'s own open question): reject the combination — a document picks one topology model, not both — but this spec does not mandate it. See [Reconciliation notes](#6-reconciliation-notes), item 5.

#### 4.10.4 Runtime landing: region id → zone id convergence

**The runtime substrate already exists; regions extend it rather than replacing it.** Authored `region.id` compiles to the toolkit's existing `RegionData.ID`, which already stamps `ZoneID` on the perception/knowledge layer (`encounter/perception/knowledge.go`'s `HexObservation`, `encounter/knowledge.go`'s `refreshObservations` via `Space.RegionAt(h)`) and is carried on the wire today as `HexRecord.zone_id` ("optional zone membership"). **A connector's own `DoorID` (`fmt.Sprintf("%s-door-%s-%s", key, from, to)`, where `from`/`to` are room IDs) is a physical-layout identity, constructed the same way whether or not `regions:` exist — it is not, and must never become, a region identity.** Point 8 above (§4.10.2) states this directly: repainting or deleting a region must never rename a connector door's ID, nor an authored edge's endpoint-derived `AuthoredDoorID` (§4.7). Read the two door-identity mechanisms as parallel and independent of region identity, not as a place region ids get wired into.

- The per-hex stamp carries the **innermost** authored region's id; `zone_id == ""` continues to mean root/space on the compatibility wire.
- A minimal runtime addition is derived `Zone.parent_id` (absent means root) — the wire-level analog of §4.10.2's derived parent relationship, letting a runtime consumer walk the same chain the compiler derived without re-deriving containment itself.
- Runtime zone metadata must stay **fog-authorized**: disclose the innermost zone and required ancestor chain for cells the observing player has actually seen, never a global hidden cell-to-region map. Adding a full cell list to runtime `Zone` would duplicate authoring truth and disclose unseen geometry — it is explicitly not proposed.
- Today's compiler already does a strict 1:1 room→region compile via `compileRoom` → `DungeonRegionParams`, using the identical archetype vocabulary (`entrance | chamber | corridor | boss`). #180/v0.3 is authors painting *more* of that same structure — including nested ones — onto the mechanism that already drives fog, spawn seeding, and door naming, not inventing a second runtime concept.
- **Why region ids must be stable**: every future per-scope semantic (audio triggers, lighting scopes, quest references, fog memory — the extension seam §4.10.2 point 5 exists for) hangs off the id. Repainting a region's cells must not change its id, or every attached future semantic loses its attachment point on the next edit.

#### 4.10.5 Extension seam

Preserve a generic future-property extension seam and the current location-to-scope lookup only. This cut does **not** add lighting/audio/trigger capability blocks to `RegionDoc` — it only guarantees that when a future spec level adds one, it resolves through the same per-property innermost-outward walk (§4.10.2 point 5) already specified here, not a new resolution mechanism.

**Acceptance criteria:**
- Strict region decode/validation rejects empty, duplicate-cell, non-contiguous, and equal/partially-overlapping cell sets with author-facing errors naming the specific cells or regions involved.
- Containment derivation is proven for at least a 2-deep nesting (a region strictly inside another), including correct parent-ID/innermost-index derivation and stable behavior across repaint/delete of the inner region.
- A boss-archetype region's boss-cell membership check supersedes room-archetype boss validation the moment any `regions:` are declared, with no double-validation.
- `Load` recomputes persisted parent/index and rejects on disagreement.
- Runtime projection exposes `Zone.parent_id` and per-hex innermost `zone_id`, fog-authorized, with no hidden-extent disclosure.
- No region boundary appears as a `FloorPlanEdge` record unless an independent `walls:` entry (§4.7) also exists on that same edge.
- **Not required by this list**: authoring-wire projection of region extents or a derived parent id on `FloorPlan` — `plan.md:22`/the platform checkpoint ask for it; this spec does not yet mandate it. See [Reconciliation notes](#6-reconciliation-notes), item 6, an open ratification point.

## 6. Reconciliation notes

Disagreements found between sources while drafting this spec, and how each is resolved here. Per instruction, flagged rather than silently resolved.

1. **`extent: {min,max}` vs. `cells:` for region shape.** The [Specimen Pack v0.2 comment](https://github.com/KirkDiggler/rpg-project/issues/175#issuecomment-5185751479) on rpg-project#175 (2026-08-04, "canonical target") used rectangle `extent: {min: [c,r], max: [c,r]}` for every region example. This directly contradicts `TARGET-YAML.md`'s settled shape, the #180 discovery comment's own concrete proposal (`cells: [[9,2],[9,3],...]`), and the specimen pack the builder actually generates and round-trips through real mutators (`createRegion`/`addCellToRegion`/...). **Resolution: `cells:` wins.** Kirk has ruled out `extent:` rectangles for regions; `extent:` may return in a future spec level as authoring *sugar* that expands to `cells:` at parse time, but never as the storage/acceptance grammar. §4.10.1 states this explicitly. **Named debt, not fixed in this PR**: `ideas/dungeon-builder/design.md:5` and `ideas/dungeon-builder/plan.md:7`, both on `main` today, still open by pointing to that same superseded comment as "the target grammar and acceptance authority" — an implementer starting from `plan.md` (the merged wave doc, where they will start) follows that line straight to the rectangle grammar this item rejects. This PR's header names both lines explicitly for exactly that reason, but does not edit `design.md`/`plan.md` themselves — different doc lineage, tracked here as a follow-up edit those two files need on `main` once this spec is ratified.
2. **Flat/disjoint-only vs. nesting-by-containment for regions.** `TARGET-YAML.md`'s own "Invariants — validated client-side" section states a bare "**Non-overlapping** — no cell may belong to more than one region at once," with no containment exception, and its "Open questions" section does not mention nesting at all. This reflects the client's *current* implementation (`regionGeometry.ts`, `validateRegionCells`), which predates the five-comment "regions are scopes" refinement on rpg-project#180 (2026-08-04 19:27–21:50). `ideas/dungeon-builder/design.md`/`plan.md` already carry the *later*, nesting-capable language ("the parent is the smallest strict superset... disjoint regions are siblings; equal or partial overlap is invalid"). **Resolution: the nesting-by-containment model wins for this contract** (§4.10.2) — it is what `design.md`/`plan.md`/the #180 issue body already ratify, and what this spec is a contract *for*, not a description of what one existing client build already exercises. The client-side validator will need a follow-up round to actually author a nested region through the UI; that gap is real and is noted here, not hidden.
3. **"Complete absolute extents" (design.md/plan.md's own wording) is ambiguous** between "extent" as an abstract cell-set description and "extent" as the literal `extent: {min,max}` rectangle grammar item 1 above rejects. **Resolution**: read "extents" in `design.md`/`plan.md` as the abstract sense (a region's complete, explicit cell membership) — consistent with item 1's resolution — never as an endorsement of rectangle grammar.
4. **Canvas-mode vs. room-chain-mode exclusivity is unstated by every source.** Neither `design.md`/`plan.md`, rpg-project#192, nor `TARGET-YAML.md` states what happens if a document declares both non-empty `rooms:` and a `canvas:` block. §4.5 records a recommendation (reject the combination) but does **not** treat it as ratified — it needs an explicit Kirk call, the same way the `rooms:`/`regions:` precedence question (item 5) does.
5. **Whether a document may combine non-empty `rooms:` with declared `regions:` is the one open question here — precedence itself is already settled.** §4.2 ("Superseded when `regions:` are declared") and §4.10.2 point 7 ("Archetype authority follows scopes, exclusively") already state, per the 19:27 comment and the platform checkpoint, that region scopes win over room archetypes for validation the moment any `regions:` exist — that part is not open. What `TARGET-YAML.md`'s own open question actually leaves unresolved is narrower: whether the *combination itself* (both constructs non-empty in one document) should be flatly rejected outright, or silently tolerated with regions simply taking validation precedence. §4.10.3 states only that narrower question as open.
6. **The authoring-projection scope in §4.5/§4.10 is thinner than what `plan.md`/`design.md`/the platform checkpoint ask for, on both waves — found while drafting, not resolved.**
   - **Wave 0.** `plan.md:13` asks the proto to define "authoring canvas dimensions, **projected canonical structural-floor cells**, and canonical physical edges"; `design.md:11` says "Authoring projection exposes those explicit canonical cells and canonical physical edges." §4.5 requires only dimensions (`rooms: []` + `canvas.width`/`canvas.height`) plus authored edges — no projected floor-cell list. This spec faithfully transcribed #192's own scope item 6, which is itself dimensions-only; #192 and `design.md`/`plan.md` disagree with *each other* here, and this spec inherited #192's side without flagging it, until now.
   - **Wave 1.** `plan.md:22` asks for "authoring extents plus toolkit-derived parent ID and runtime `Zone.parent_id`"; the platform checkpoint says "A minimal runtime addition is derived `Zone.parent_id`, while the authoring FloorPlan needs explicit region extents." §4.10's acceptance criteria cover only the runtime side (`Zone.parent_id`, per-hex innermost `zone_id`, fog-authorized) — nothing requires the authoring wire to carry region extents or the derived parent id. Today's `FloorPlan` (`dnd5e/api/authoring/v1alpha1/service.proto:87-133`) carries `rooms`/`connectors`/`height`/`door_row`/`entrance`/`edges` and nothing region-shaped — this is real, currently-unrequested proto surface, not an oversight in an existing field.

   **Both positions, and a recommendation.** For the fuller projection: an authoring board needs to *render* the compiled result, not just validate against it — with no floor-cell/extent echo, a client either re-derives geometry itself (the re-canonicalization the Boundary Rule forbids) or renders only what it locally authored, which silently disagrees with the server the moment authored and server-derived content interact. For the leaner dims-only wire this spec currently specifies: it's the minimum a client already holds from its own outgoing `PutDungeon` call, and every added `FloorPlan` field is permanent proto surface and a second place truth can drift from `regions:`/`canvas:` themselves. **Recommendation: adopt the wave docs' fuller projection** (projected floor cells for Wave 0; extents plus derived parent id for Wave 1) — the rendering need is concrete and immediate, the leaner wire's savings are speculative. This is a genuine Kirk/platform ratification point; §4.5's and §4.10's acceptance criteria are deliberately **not** amended to require it until that ratification happens.
7. **`RegionDoc.archetype` is required in the builder's real TypeScript type, while this spec (following `design.md`/#180) makes it optional.** `dungeonYaml.ts`'s `RegionDoc` declares `archetype: string` (not `archetype?: string`), and `createRegionNode` (`dungeonYaml.ts:1858-1867`) sets `obj.archetype` unconditionally while gating `name` on truthiness — the client cannot author a region with an inherited/omitted archetype today. The contract direction in §4.10.1/§4.10.3 (optional, inherits per §4.10.2 point 5) is correct per #180's body and `design.md:13`, both of which say archetype is optional and inherits when omitted; this is the same class of client-behind-the-model gap as item 2 above, and — per this appendix's own discipline — it should have been listed there and wasn't. Flagged now: a future builder round needs to make `archetype` genuinely optional client-side to match this contract.
